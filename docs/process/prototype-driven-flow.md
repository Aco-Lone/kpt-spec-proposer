# プロトタイプ駆動KPTフローの手順書（ツール非依存）

この文書は、GitHub Copilot Coding Agentという実装手段に依存しない、プロセス自体の説明です。将来的に別のツールでこのプロセスを再現する場合はこの文書を参照してください。

## サイクル

1. **要望の受付**: シンプルな要望を受け付ける。規模（light/full）を判定する。
2. **プロトタイピング**: 要望または前回の改善提案をもとに、画面操作可能なモックを作る。実データ・永続化・認証等は簡略化してよい。簡略化した点は必ず記録する。
3. **KPTレビュー**: プロトタイプに触れた人間が、Keep（良い点）/Problem（課題）/Try（次に試すこと）を記入する。
4. **KPT集約**: 記入されたKPTを集約し、重複や矛盾を整理する。
5. **曖昧点の解消**: 集約結果に曖昧な点（範囲・優先度・対象者・成功基準の不明確さ）があれば、選択式の質問にまとめて確認する。曖昧点がなくなるまで改善提案には進まない。
6. **改善提案とループ判定**: Try起点で改善案を提示し、あわせて「まだプロトタイプで検証すべきか」「仕様として確定してよいか」を判定材料とともに提示する。
7. **分岐**:
   - 継続プロトタイピングの場合: 改善提案を次のプロトタイピング（手順2）への入力とし、サイクルを繰り返す。
   - 仕様化の場合: 人間が承認したうえで、システム非依存の仕様書（spec.md相当）を作成する。
8. **仕様確定後も継続**: 仕様書の確定はプロセスの終了ではなく、その時点のスナップショットである。以降もプロトタイピングとKPTは続き、仕様書との差分は変更履歴として記録し続ける。

## 設計思想

- **曖昧なまま次工程に進めない**: 人間の記述は省略されがちなため、解釈違いによる手戻りを防ぐ目的で、曖昧点の解消を仕様化の前工程に必ず挟む。
- **仕様化は人間の承認を必須とする**: 自動化された提案をそのまま仕様として確定させない。
- **要望の重さに応じてプロセスの重さを変える**: 小さな要望にフルプロセスを強制すると使われなくなるため、light/fullの分岐を設ける。
- **仕様確定をゴールにしない**: プロトタイプとKPTのループは仕様確定後も継続し、仕様書は都度更新されるスナップショットとして扱う。
