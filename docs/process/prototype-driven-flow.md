# プロトタイプ駆動KPTフローの手順書（ツール非依存）

この文書は、GitHub Copilot Coding Agentという実装手段に依存しない、プロセス自体の説明です。将来的に別のツールでこのプロセスを再現する場合はこの文書を参照してください。

## サイクル

1. **要望の受付**: シンプルな要望を受け付ける。
2. **プロトタイピング**: 要望または前回の改善提案をもとに、画面操作可能なモックを作る。実データ・永続化・認証等は簡略化してよい。簡略化した点は必ず記録する。
3. **KPTレビュー**: プロトタイプに触れた人間が、Keep（良い点）/Problem（課題）/Try（次に試すこと）を、種別・機能カテゴリ・内容・状態の列を持つ表（スプレッドシート等）で記入する（種別ごとに1行）。
4. **KPT取り込みと集約**: 記入されたKPTを構造化データ（CSV）として取り込み、機能カテゴリ別の論点IDを付けたワイド形式（1論点=1行、Keep/Problem/Tryを各列に束ねる）の表に集約して重複や矛盾を整理する。論点IDは取り込み時に付与し、ラウンドをまたいで同一論点を追跡できるよう再利用する。あわせて各論点が「仕様（WHAT）」の話か「機能独自のデザインルール（見た目・操作感）」の話かの区別（対象）を付与し、さらに各論点が既存feature改善か新featureとして切り出すべきかを判別する。区別・判別も取り込み時に付与し、迷う場合は仕様／既存feature改善を既定とする。
5. **曖昧点の解消**: 集約結果に曖昧な点（範囲・優先度・対象者・成功基準の不明確さ、仕様/デザインの区別不能、既存feature改善/新featureの判別不能、既存デザインルールとの矛盾）があれば、選択式の質問にまとめて確認する。曖昧点がなくなるまで改善提案には進まない。
6. **改善提案とループ判定**: Try起点で改善案を提示し、あわせて「まだプロトタイプで検証すべきか」「仕様として確定してよいか」を、仕様/デザインの区別ごとに判定材料とともに提示する。既存featureのスコープを超える論点があれば新feature切り出し候補もあわせて提示する（実行は人間の承認後）。
7. **分岐**:
   - 継続プロトタイピングの場合: 改善提案を次のプロトタイピング（手順2）への入力とし、サイクルを繰り返す。プロトタイピングは確定済みのデザインルールがあればそれに準拠する。
   - 新feature切り出しの場合: 人間が承認したうえで、新しいfeature-nameで要望を起票し、別の成果物ディレクトリとして手順1から新たなサイクルを開始する。元featureのサイクルはそのまま継続する。
   - 仕様化の場合: 人間が承認したうえで、システム非依存の仕様書（spec.md相当）と、機能独自のデザインルール（rule.md相当）を分けて作成する。仕様書に見た目・操作感のルールを混ぜない（可搬性のため）。
8. **仕様確定後も継続**: 仕様書・デザインルールの確定はプロセスの終了ではなく、その時点のスナップショットである。以降もプロトタイピングとKPTは続き、各成果物との差分は変更履歴として記録し続ける。

## 設計思想

- **曖昧なまま次工程に進めない**: 人間の記述は省略されがちなため、解釈違いによる手戻りを防ぐ目的で、曖昧点の解消を仕様化の前工程に必ず挟む。
- **仕様化は人間の承認を必須とする**: 自動化された提案をそのまま仕様として確定させない。

- **仕様確定をゴールにしない**: プロトタイプとKPTのループは仕様確定後も継続し、仕様書は都度更新されるスナップショットとして扱う。
