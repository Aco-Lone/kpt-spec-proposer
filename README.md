# kpt-spec-proposer

プロトタイプ開発をKPTで進め、仕様（spec）を固めるための agent plugin です。

シンプルな要望から画面操作可能なモックを作り、人間が記入したKPT（Keep/Problem/Try）をagentが集約・整理し、曖昧な点を質問しながら改善提案を行います。**人間が「必要な機能を搭載できた」と判断したとき**にシステム非依存の`spec.md`（仕様）へ落とし込み、見た目・操作感の`rule.md`（機能独自のデザインルール）はプロトタイピングの中で承認なしに適宜更新します。プロトタイプとKPTは1回で終わらず、ループし続けることを前提としています。

## ルール
- **プロンプトは簡潔に保つこと**
  - 括弧で補足はしない
  - 同じことを複数の箇所で書かない
  - 余分なバリデーションや説明は書かない

## 全体像

```
要望Issue
   → prototype-agent（モック生成 + 必要なら rule.md を承認なしで更新）
   → 人間がKPTを取り込み（CSVコミット / Issue貼付け / 自由文記入）
   → kpt-agent（集約・曖昧点質問・改善提案。仕様化の可否は判定しない）
   → 人間が次のいずれかを選ぶ:
     a) 改善提案をもとに prototype-agent に戻る（通常のループ）
     b) 「必要な機能を搭載できた」と判断したら、当該ラウンドの最終ステップとして spec-writer を明示起動
        → spec.md（仕様）を生成・更新 → 本開発（実装）チームへハンドオフしループ終了
```

プロセスの正本は [AGENTS.md](AGENTS.md)（責任分界・厳守事項・詳細ルールの所在）と各skillファイルです。ツール非依存の手順は [docs/process/prototype-driven-flow.md](docs/process/prototype-driven-flow.md) を参照してください。

## エージェントの起動方法（運用の二重化）

各エージェント定義（`.github/agents/*.md`）の frontmatter には、工程遷移を1クリックで進められる宣言的 `handoffs`（ボタン）を設定しています。起動経路は環境によって異なります。

- **IDE（VS Code 等）**: 完了時に表示される handoff ボタンで、蓄積コンテキストごと次工程へ引き継げます。
- **クラウド（GitHub.com のIssue運用）**: handoff は未サポートの可能性があるため、対象エージェントを手動でメンション・アサインして起動します。
- どちらの経路でも、`spec-writer`の起動には**人間の明示的な起動**が必須です。`rule.md`の更新は`prototype-agent`が承認なしで行うため、専用の起動ボタンを持ちません。

## 入力仕様（要点）

詳細は各skillファイルを正本とし、ここでは入力時に知っておくべき要点のみを示す。

- **KPT CSVのヘッダ**: `機能カテゴリ,Keep,Keep状態,Problem,Problem状態,Try,Try状態`（この順で7列固定、1行=1論点）。状態は内容が非空の列のみ必須。→ [kpt-parsing](.github/skills/kpt-parsing/SKILL.md)
- **KPTの取得元**: 「コミット済みCSVパス」「Issue本文への貼り付けCSV」「自由文記入」のいずれか。自由文の場合はagentがCSV形式に整形して`roundN.csv`に保存する。CSVパスと貼り付けを両方指定した場合は内容が一致しないと処理を中断する。→ 同上
- **spec化のタイミング**: 人間が`spec-writer`を明示起動したときのみ。当該ラウンドの最終ステップとして行い、生成後は本開発チームへハンドオフしてループを終了する（agentは仕様化の可否を判定しない）。→ [spec-writer](.github/agents/spec-writer.md)
- **rule.mdの更新**: `prototype-agent`が各ラウンドで承認なしに適宜更新する。各ルール項目は一文の短い箇条書きのみとし、意図・理由は書かない。→ [prototype-agent](.github/agents/prototype-agent.md)

## 設計判断の記録

この構成に至るまでに検討し、採用しなかった選択肢も含めて記録します。

- **なぜエージェントを3体に絞ったか**: 当初は「モック生成」「KPT集約」「曖昧点質問」「仕様化」の4体案だったが、非同期のメンション起動モデルではフェーズごとの手動切り替えが呼び忘れ・手戻りを生む。性質が近い「KPT集約」と「曖昧点質問」を`kpt-agent`に統合し内部で分岐させた。処理の性質が明確に異なる「コード生成」と「文書生成」は`prototype-agent`と`spec-writer`に分離したままにしている。
- **なぜ曖昧点の質問を一問ずつ対話的に確認するか**: 複数の曖昧点を一度に列挙すると人間が読み飛ばし・雑な一括回答をしがちで、解釈違いによる手戻りにつながる。`ambiguity-detection`に従い1つの論点を推奨回答付きで掘り下げてから次に進むことで回答の精度を上げる。往復は同一セッション内の対話で完結させ、複数セッションには分割しない。
- **なぜspec化を人間の判断だけに委ねるか**: 当初は`kpt-agent`が収束度・Keep/Problem比率から仕様化を提案する`readiness-check`を持たせていたが、「specを起こすのは人が必要な機能を搭載できたと判断した時」という実態と合わず、誤ったタイミングでの仕様化を誘発するリスクがあった。同スキルは廃止し、`kpt-agent`は仕様化の可否を一切判定しない。
- **なぜrule.mdに承認ゲートを設けないか**: 見た目・操作感のルールはプロトタイピングの中で自然に固まる性質で、「確定」という節目の判断を必要としない。承認トリガーを増やすとプロセス摩擦が上がるだけなので、デザイン判断の主体である`prototype-agent`が承認なしで更新する。生きた記録は`prototype-notes.md`、固まったルールは`rule.md`。
- **なぜKPTを表形式＋機能カテゴリ論点IDで管理するか**: 文章のまま蓄積するとラウンドをまたいだ同一論点の追跡が文面照合に依存して不安定になる。1論点=1行のワイド形式に安定した論点IDを振ることで「今どう評価され、何が課題で、次に何を試すか」を横断で読める。IDの接頭辞は種別ではなく機能カテゴリとし、同じ機能領域のフィードバックをまとめられるようにした。論点IDと対象は集約時にagentが付与し、人間の記述負荷を増やさない。
- **なぜKPTをスプレッドシート管理＋CSV取り込みにしたか**: KPTを既存のスプレッドシートで管理しているチームが多いため。取得元に依らずCSV本体を入力として扱い、現在の優先方法は`docs/kpt/kpt-log/roundN.csv`へのコミット（このファイルがそのまま生ログになる）。一方で集約結果はGitHub上で表として読めるMarkdown表にしている。KPTは機能横断のフィードバックのため、特定featureのフォルダには入れずリポジトリ横断の`docs/kpt/`に置く。
- **なぜKPT入力にCSVだけでなく自由文も許すか**: CSV作成自体が心理的ハードルになりKPT記入が滞ることを避けるため。自由文で受け取ってもagentがCSV形式に整形してから`roundN.csv`に保存するため、生ログの形式・不可変性は変わらない。
- **なぜspec.mdをシステム非依存のMarkdownにしたか**: プロセス自体はCoding Agentに依存するが、成果物は他ツール（Notion / Jira 等）へそのまま転記・移植できるようにしたい。可搬性のため、GitHubに依存しない手順書も`docs/process/`に用意している。
- **なぜspec化をラウンドの最終ステップとし、生成後にループを終了するか**: 当初はspec.md生成後もループを継続する運用だったが、「本開発へのハンドオフ地点」が曖昧なまま気づきを反映し続けると、本開発チームがどの時点の仕様に追従すべきか判断できなくなる。spec化を当該featureのラウンドの最終ステップと定め、生成後は本開発（実装）チームへハンドオフしてそのfeatureのプロトタイピング/KPTループを終了する運用に改めた。
- **なぜspec.mdとrule.mdを分離したか**: spec.mdに配色・余白・遷移を混ぜると実装スタックへの依存が仕様に染み出し、可搬性という設計意図に反する。またデザインルールは複数の仕様から参照されうる共有資産で、複製するとドリフトを招く。確定の仕方も非対称（spec=人間の判断、rule=承認なし）にしている。
- **なぜdesign.mdを最初のプロト作成時に確定するか**: デザインルールは3層（spec / rule / design）。`design.md`は独自に育てる共有ルールではなく、Material Design のような**確立済み外部標準への準拠宣言と基本トークンの記録**。最初のモックは必ず何らかのフォント・余白・配色で作られる＝初回時点で暗黙に確定しているため、初回セッションで明文化する。外部標準を参照するだけなので空箱にならない。横断共有が本質なので`docs/design.md`に置く。
- **なぜ「対象」をagentが付与し安定化させるか**: 人間に書かせると記述負荷が増える（IDと同じ方針）。ただし判定がラウンドごとに揺れると成果物の振り分けが不安定になるため、一度確定した対象は再利用し、迷ったら`spec`を既定として、真に判別不能なものだけを質問化する。
