# kpt-spec-proposer

プロトタイプ開発をKPTで進め、仕様（spec）を固めるための agent plugin です。

シンプルな要望から画面操作可能なモックを作り、人間が記入したKPT（Keep/Problem/Try）をagentが集約・整理し、曖昧な点をagentが質問しながら改善提案を行い、最終的にシステム非依存の`spec.md`へ収束させます。プロトタイプとKPTは1回で終わらず、ループし続けることを前提としています。

## 全体像

```
要望Issue
   → prototype-agent（モック生成）
   → 人間がKPTをスプレッドシートで管理しCSVを取り込み
   → kpt-agent（集約・曖昧点質問・改善提案・ループ判定）
   → 「継続プロトタイピング」なら prototype-agent に戻る
   → 「仕様化」なら人間承認を経て spec-writer がトラック別に spec.md（仕様）・rule.md（機能独自のデザインルール）を生成（spec先行確定、rule後追い確定を許容）
   → spec.md確定後もループは継続
```

## エージェントの起動方法（運用の二重化）

各エージェント定義（`.github/agents/*.md`）の frontmatter には、工程遷移を1クリックで進められる宣言的 `handoffs`（ボタン）を設定しています。ただし起動経路は環境によって異なります。

- **IDE（VS Code 等）**: エージェント完了時に表示される handoff ボタンを押すことで、プロンプトと蓄積コンテキストごと次工程のエージェントへ引き継げます。
- **クラウド（GitHub.com のIssue運用）**: handoff は未サポートの可能性があるため、従来どおり対象エージェントを手動でメンション・アサインして起動してください。
- どちらの経路でも、`spec-writer`（仕様化）の起動には人間の明示的な承認が必須である点は変わりません。

## リポジトリ構成

```

    prototype-agent.md           要望/改善提案 → モック生成・更新
    kpt-agent.md                 KPT集約 + 曖昧点抽出 + 改善提案 + ループ判定
    spec-writer.md               仕様化承認後にspec.mdを生成・更新し、ruleトラック収束後にrule.mdを生成・更新
  skills/
    mock-scaffolding/SKILL.md        モック実装時の簡略化ルール
    web-mock-stack/SKILL.md          WebモックのVite + React + TypeScript構成・配置・プレビュー手順
    kpt-parsing/SKILL.md             KPTの抽出・分類・対象付与・生ログ保存ロジック
    ambiguity-detection/SKILL.md     曖昧点の判定ロジック（対象判別・rule矛盾を含む）
    readiness-check/SKILL.md         トラック別の「継続プロトタイピング」か「仕様化」かの判定材料
    spec-template/SKILL.md           システム非依存のspec.mdフォーマット
    design-rule-template/SKILL.md    機能独自のデザインルール rule.md のフォーマット
    change-history-logging/SKILL.md  ラウンドごとの変更履歴の追記ルール
  ISSUE_TEMPLATE/
    01_feature-request.yml       要望入力（feature-nameを指定）
    02_kpt-feedback.yml          KPT取り込み（スプレッドシートのCSVをコミット・貼付け、feature-nameで対応づけ）

mocks/<feature-name>/                画面操作可能なモック本体（Vite + React + TypeScript、web-mock-stackスキルに従う）

docs/
  process/
    prototype-driven-flow.md     GitHubに依存しないプロセス手順書（可搬性のため）
  specs/
    <feature-name>/
      request.md                 元の要望
      prototype-notes.md         ラウンドごとの変更点・簡略化点・デザイン判断（追記蓄積）
      kpt-log/roundN.csv         KPTの生ログ（スプレッドシートから取り込んだCSV。削除・改変しない）
      kpt-summary.md             kpt-agentによる集約結果（Markdown表・ワイド形式＋論点ID＋対象、毎ラウンド更新）
      clarification-log.md       曖昧点の質問と回答（曖昧点がある場合）
      spec.md                    仕様（WHAT）。specトラック収束・人間承認後に生成
      rule.md                    機能独自のデザインルール（見た目・操作感）。ruleトラック収束・人間承認後に生成（specより後追い確定も可）
```

## 入力仕様（要点）

詳細な判定ロジックは各skillファイルを正本とし、ここでは利用者が入力時に知っておくべき要点のみを示す。

- **feature-nameの形式**: `^[a-z0-9]+(?:-[a-z0-9]+)*$`（半角小文字英数字とハイフンのみ）。詳細は [AGENTS.md](AGENTS.md)「feature-nameの検証」を参照。
- **KPT CSVのヘッダ**: `種別,機能カテゴリ,内容,状態`（この順で4列固定）。詳細は [kpt-parsing/SKILL.md](.github/skills/kpt-parsing/SKILL.md)「入力検証」を参照。
- **状態の許容値**: 種別ごとに異なる（Keep=`継続`のみ／Problem・Try=`未対応`|`対応中`|`解消済み`等）。詳細は同スキルを参照。
- **CSVの取得元**: 「コミット済みCSVパス」または「Issue本文への貼り付け」の少なくとも一方が必須。両方指定時は内容が一致しないと処理を中断する。詳細は同スキルを参照。
- **最新表とラウンド履歴**: `kpt-summary.md`の`KPT一覧`は論点ごとの最新スナップショット（上書き）、`ラウンド履歴`はラウンドごとの観測の追記（削除・改変しない）。詳細は同スキルを参照。
- **spec先行・rule後追い確定**: specトラックが収束すればruleが未収束でも仕様化（spec.md確定）を提案できる。rule確定はspec確定後に別途提案される。詳細は [readiness-check/SKILL.md](.github/skills/readiness-check/SKILL.md)を参照。

## 設計判断の記録

この構成に至るまでに検討し、採用しなかった選択肢も含めて記録します。

### なぜエージェントを2〜3体に絞ったか

当初は「モック生成」「KPT集約」「曖昧点質問」「仕様化」を4つの独立したカスタムエージェントに分ける案を検討しました。しかし、GitHub Copilot Coding Agentは基本的にIssue/PRへのメンションで起動する非同期モデルであり、フェーズが変わるたびに人間が「次はこのagentを呼ぶ」と手動で切り替える必要がありました。これは呼び忘れや手戻りの原因になるため、性質が近い「KPT集約」と「曖昧点抽出・質問」を`kpt-agent`という1つのエージェントに統合し、内部で条件分岐（曖昧点があれば質問して中断、なければ改善提案へ進む）させる設計にしました。

一方で「モック生成（コード生成）」と「仕様書生成（文書生成）」は処理の性質が明確に異なるため、`prototype-agent`と`spec-writer`は分離したままにしています。

### なぜ曖昧点の質問を1セッション内で完結させるルールにしたか

Coding Agentは同期対話ではなく、Issueコメント→セッション再起動という非同期・低頻度なやりとりです。質問のたびにセッションを立ち上げて人間の回答を待つ往復を繰り返すと、待ち時間とコストが積み重なります。そのため「曖昧点は1回のセッションでまとめて出し切り、人間は1回でまとめて回答する」という往復回数を最小化するルールをAGENTS.mdに明記しました。

### なぜ仕様化を自動連鎖させず、人間の承認を必須にしたか

KPTからの改善提案は、プロトタイプでさらに検証すべきものと、仕様として確定してよいものが混在します。`kpt-agent`が「仕様化してよい」と判断した内容を自動でそのまま`spec-writer`に渡してspec.mdを確定させてしまうと、検証不足のまま仕様が固まるリスクがあります。そのため`kpt-agent`はあくまで判定結果（readiness-checkの材料）を提示するだけにとどめ、`spec-writer`の起動は必ず人間の明示的なアクションを挟む設計にしています。

### なぜKPTを表形式＋機能カテゴリ論点IDで管理するか

KPTの項目を文章のまま蓄積すると、ラウンドをまたいだ同一論点の追跡が文面の照合に依存し、収束判定（readiness-check）が不安定になります。そこで集約結果を`論点ID | 機能カテゴリ | 対象 | Keep | Problem | Try | Status`のワイド形式（1論点=1行）の表にし、各論点に安定した論点IDを付与しました。1つの論点に対するKeep/Problem/Tryを1行に束ねることで、「この論点は今どう評価され、何を課題とし、次に何を試すか」を横断で読めるようにしています。論点IDの接頭辞は「Keep/Problem/Tryの種別」ではなく「機能カテゴリ（プロトタイプの機能領域）」とし、同じ機能領域のフィードバックをラウンド横断でまとめられるようにしています。論点IDと対象（spec/rule）は集約時に付与し、人間の入力（生ログ・KPTのCSV）には振らないことで、人間の記述負荷を増やさずに追跡性を得ています。

### なぜKPTをスプレッドシート管理＋CSV取り込みにしたか

KPTは既存のスプレッドシートで管理しているチームが多く、その運用に合わせて「スプレッドシートで管理→CSVで取り込む」方式を採用しました。入力CSVのカラムは `種別,機能カテゴリ,内容,状態`で、種別ごとに1行で記入し、論点IDは含めません（集約時にagentが付与し、Keep/Problem/Tryの束ねも集約時に行う）。現在の優先方法は `docs/specs/<feature-name>/kpt-log/roundN.csv` へのコミットで、このファイルがそのまま生ログになります。将来的にIssueフォームへのCSV貼り付けに切り替えられるよう、取得元に依らずCSV本体を入力として扱います。一方で集約結果（`kpt-summary.md`）は、GitHub上で表として読めてreadiness-checkの人間レビューに有利なためMarkdown表のままにしています。

### なぜspec.mdをシステム非依存のMarkdown形式にしたか

プロセス自体（Issueテンプレートやカスタムエージェント）はGitHub Copilot Coding Agentに強く依存しますが、成果物であるspec.mdは他のツール（Notion、Jira、他のSDDツールなど）にそのまま転記・移植できるよう、特定システムの記法に依存しない見出し構造のみのフォーマットにしています。プロセスの可搬性を高めるため、`docs/process/prototype-driven-flow.md`にGitHubに依存しない手順書も別途用意しています。

### なぜプロトタイプ→KPTのループがspec.md確定後も終わらない設計にしたか

spec.mdの確定を「開発の終点」として扱うと、確定後に得られた新しい気づき（KPT）を反映する仕組みがなくなってしまいます。そのため、spec.md確定はあくまで「その時点のスナップショット」と位置づけ、以降もプロトタイプの改善とKPTの記入は継続し、spec.mdとの差分は`change-history-logging`スキルを通じて追記していく運用にしています。

### なぜ仕様（spec.md）とデザインルール（rule.md）を分離したか

`spec.md`は他ツール（Notion / Jira 等）へ転記できるシステム非依存のWHATを狙っています。ここに配色・余白・遷移などのデザインルールを混ぜると、実装スタックへの依存が仕様に染み出し、可搬性という設計意図に反します。またデザインルールは複数の仕様から参照される共有資産になりうるため、仕様に複製するとドリフト（不整合）を招きます。そこで見た目・操作感のルールは`rule.md`（`design-rule-template`スキル）に分離し、`spec.md`は仕様のみを保持します。KPT項目には集約時に`対象`（`spec`/`rule`）を付与して、どちらの成果物を改善する材料かを追跡します。

### なぜデザインルールを最初から3層（spec/rule/design）にしなかったか

当初は「基本デザインルール（共有）＝`design.md`」と「機能独自デザインルール＝`rule.md`」を同時に立てる案も検討しました。しかし「基本＝横断的に共通」かどうかは複数featureが揃って初めて判断でき、feature が少ない初期は事実上すべて`rule.md`に溜まります。共有の`design.md`を先に作ると中身が育たないまま形骸化し、昇格ロジックも動きません。そこで段階導入とし、本フェーズは`spec.md`＋`rule.md`の2層で回します。`design.md`への昇格は`readiness-check`が「昇格候補」フラグを観測するにとどめ、候補が実証された段階で人間が`design.md`・横断オーナー・専用承認ゲートの導入（Phase 2）を判断します。

### なぜデザインルールの確定に専用エージェントを新設しなかったか

`design-writer`のような専用エージェントを増やすと、非同期・手動起動のCoding Agentでは「呼び忘れ」が増え、確定トリガーが増殖してプロセス摩擦が上がります（エージェントを2〜3体に絞った理由と同じ）。そこで`rule.md`の確定も同じ`spec-writer`が担いますが、収束はspec/ruleそれぞれのトラックで別々に判定するため、確定タイミングは必ずしも同時ではありません（spec先行確定、rule後追い確定を許容）。ラウンドごとの生きたデザイン判断は`prototype-notes.md`に記録し、確定版だけを`rule.md`に切り出します。プロトタイプがルールを守る導線として、`prototype-agent`は着手前に既存`rule.md`を必須参照します。

### なぜ「対象」をagentが付与し安定化させるのか

KPT項目を`spec`/`rule`に振り分ける「対象」を人間に書かせると記述負荷が増えます（IDを人間に振らせない方針と同じ）。そのため対象は`kpt-agent`が集約時に付与します。ただし対象判定はラウンドごとに揺れると収束判定（`readiness-check`）が不安定になるため、一度確定した対象は同一IDで再利用し、迷ったら`spec`を既定とするデフォルト規則を置いて、真に判別不能なものだけを質問化して往復コストを抑えています。
