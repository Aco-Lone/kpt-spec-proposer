# kpt-spec-proposer

プロトタイプ開発をKPTで進め、仕様（spec）を固めるための agent plugin です。

シンプルな要望から画面操作可能なモックを作り、人間が記入したKPT（Keep/Problem/Try）をagentが集約・整理し、曖昧な点をagentが質問しながら改善提案を行います。**人間が「必要な機能を搭載できた」と判断したとき**にシステム非依存の`spec.md`（仕様）へ落とし込み、見た目・操作感の`rule.md`（機能独自のデザインルール）はプロトタイピングの中で承認なしに適宜更新します。プロトタイプとKPTは1回で終わらず、ループし続けることを前提としています。

## 全体像

```
要望Issue
   → prototype-agent（モック生成 + 必要なら rule.md を承認なしで更新）
   → 人間がKPTをスプレッドシートで管理しCSVを取り込み
   → kpt-agent（集約・曖昧点質問・改善提案。仕様化の可否は判定しない）
   → 改善提案をもとに prototype-agent に戻る（通常のループ）

   人間が「必要な機能を搭載できた」と判断したとき（ラウンドとは独立・いつでも）
   → 人間が spec-writer を明示起動 → spec.md（仕様）を生成・更新
   → spec.md 生成後もループは継続
```

## エージェントの起動方法（運用の二重化）

各エージェント定義（`.github/agents/*.md`）の frontmatter には、工程遷移を1クリックで進められる宣言的 `handoffs`（ボタン）を設定しています。ただし起動経路は環境によって異なります。

- **IDE（VS Code 等）**: エージェント完了時に表示される handoff ボタンを押すことで、プロンプトと蓄積コンテキストごと次工程のエージェントへ引き継げます。
- **クラウド（GitHub.com のIssue運用）**: handoff は未サポートの可能性があるため、従来どおり対象エージェントを手動でメンション・アサインして起動してください。
- どちらの経路でも、`spec-writer`（仕様化）の起動には**人間の判断（必要な機能が揃ったか）による明示的な起動**が必須である点は変わりません。`rule.md`の更新は`prototype-agent`が承認なしで行うため、専用の起動ボタンを持ちません。

  ISSUE_TEMPLATE/

  specs/

      kpt-log/roundN.csv         KPTの生ログ（スプレッドシートから取り込んだCSV。削除・改変しない）

## 入力仕様（要点）

詳細な判定ロジックは各skillファイルを正本とし、ここでは利用者が入力時に知っておくべき要点のみを示す。

- **feature-nameの形式**: `^[a-z0-9]+(?:-[a-z0-9]+)*$`（半角小文字英数字とハイフンのみ）。詳細は [AGENTS.md](AGENTS.md)「feature-nameの検証」を参照。
- **KPT CSVのヘッダ**: `種別,機能カテゴリ,内容,状態`（この順で4列固定）。詳細は [kpt-parsing/SKILL.md](.github/skills/kpt-parsing/SKILL.md)「入力検証」を参照。
- **状態の許容値**: 種別ごとに異なる（Keep=`継続`のみ／Problem・Try=`未対応`|`対応中`|`解消済み`等）。詳細は同スキルを参照。
- **CSVの取得元**: 「コミット済みCSVパス」または「Issue本文への貼り付け」の少なくとも一方が必須。両方指定時は内容が一致しないと処理を中断する。詳細は同スキルを参照。
- **最新表とラウンド履歴**: `kpt-summary.md`の`KPT一覧`は論点ごとの最新スナップショット（上書き）、`ラウンド履歴`はラウンドごとの観測の追記（削除・改変しない）。詳細は同スキルを参照。
- **spec化のタイミング**: `spec.md`は人間が「必要な機能を搭載できた」と判断して`spec-writer`を明示起動したときのみ生成される（agentは仕様化の可否を判定しない）。詳細は [spec-writer.md](.github/agents/spec-writer.md) を参照。
- **rule.mdの更新**: `rule.md`（機能独自のデザインルール）は`prototype-agent`が各ラウンドで承認なしに適宜更新する。詳細は [prototype-agent.md](.github/agents/prototype-agent.md) と [design-rule-template/SKILL.md](.github/skills/design-rule-template/SKILL.md) を参照。

## 設計判断の記録

この構成に至るまでに検討し、採用しなかった選択肢も含めて記録します。

### なぜエージェントを2〜3体に絞ったか

当初は「モック生成」「KPT集約」「曖昧点質問」「仕様化」を4つの独立したカスタムエージェントに分ける案を検討しました。しかし、GitHub Copilot Coding Agentは基本的にIssue/PRへのメンションで起動する非同期モデルであり、フェーズが変わるたびに人間が「次はこのagentを呼ぶ」と手動で切り替える必要がありました。これは呼び忘れや手戻りの原因になるため、性質が近い「KPT集約」と「曖昧点抽出・質問」を`kpt-agent`という1つのエージェントに統合し、内部で条件分岐（曖昧点があれば質問して中断、なければ改善提案へ進む）させる設計にしました。

一方で「モック生成（コード生成）」と「仕様書生成（文書生成）」は処理の性質が明確に異なるため、`prototype-agent`と`spec-writer`は分離したままにしています。

### なぜ曖昧点の質問を1セッション内で完結させるルールにしたか

Coding Agentは同期対話ではなく、Issueコメント→セッション再起動という非同期・低頻度なやりとりです。質問のたびにセッションを立ち上げて人間の回答を待つ往復を繰り返すと、待ち時間とコストが積み重なります。そのため「曖昧点は1回のセッションでまとめて出し切り、人間は1回でまとめて回答する」という往復回数を最小化するルールをAGENTS.mdに明記しました。

### なぜspec化を人間の判断だけに委ね、agentに提案・自動判定させないのか

KPTからの改善提案は、プロトタイプでさらに検証すべきものと、仕様として確定してよいものが混在します。当初は`kpt-agent`が収束度・Keep/Problem比率などから「仕様化してよい」を提案する`readiness-check`を持たせていましたが、「specを起こすのは人が必要な機能を搭載できたと判断した時」という運用実態と合わず、指標ベースの自動判定はかえって誤ったタイミングでの仕様化を誘発するリスクがありました。そこで`readiness-check`スキルを廃止し、`kpt-agent`は仕様化の可否を一切判定・提案しないようにしました。`spec.md`の生成は、人間が「必要な機能を搭載できた」と判断して`spec-writer`を明示起動したときにのみ行われます（起動時の唯一のゲートは未解決の曖昧点がないこと）。

### なぜrule.mdの更新に承認ゲートを設けないのか

`rule.md`（機能独自のデザインルール＝見た目・操作感）は、プロトタイピングの中で自然に固まっていく性質のもので、仕様（WHAT）のように「確定」という節目を人間が判断する必要がありません。以前は`spec-writer`が収束判定＋人間承認を経て`rule.md`を生成する設計でしたが、これは承認トリガーを増やしてプロセス摩擦を上げるだけでした。そこで`rule.md`の更新は、デザイン判断の主体である`prototype-agent`が各ラウンドで**承認なしに適宜**行うようにしました。ラウンドごとの生きたデザイン判断は`prototype-notes.md`に記録し、固まったルールを`rule.md`に反映します。プロトタイプがルールを守る導線として、`prototype-agent`は着手前に既存`rule.md`を必須参照します。

### なぜKPTを表形式＋機能カテゴリ論点IDで管理するか

KPTの項目を文章のまま蓄積すると、ラウンドをまたいだ同一論点の追跡が文面の照合に依存し、改善提案の整理が不安定になります。そこで集約結果を`論点ID | 機能カテゴリ | 対象 | Keep | Problem | Try | Status`のワイド形式（1論点=1行）の表にし、各論点に安定した論点IDを付与しました。1つの論点に対するKeep/Problem/Tryを1行に束ねることで、「この論点は今どう評価され、何を課題とし、次に何を試すか」を横断で読めるようにしています。論点IDの接頭辞は「Keep/Problem/Tryの種別」ではなく「機能カテゴリ（プロトタイプの機能領域）」とし、同じ機能領域のフィードバックをラウンド横断でまとめられるようにしています。論点IDと対象（spec/rule）は集約時に付与し、人間の入力（生ログ・KPTのCSV）には振らないことで、人間の記述負荷を増やさずに追跡性を得ています。

### なぜKPTをスプレッドシート管理＋CSV取り込みにしたか

KPTは既存のスプレッドシートで管理しているチームが多く、その運用に合わせて「スプレッドシートで管理→CSVで取り込む」方式を採用しました。入力CSVのカラムは `種別,機能カテゴリ,内容,状態`で、種別ごとに1行で記入し、論点IDは含めません（集約時にagentが付与し、Keep/Problem/Tryの束ねも集約時に行う）。現在の優先方法は `docs/specs/<feature-name>/kpt-log/roundN.csv` へのコミットで、このファイルがそのまま生ログになります。将来的にIssueフォームへのCSV貼り付けに切り替えられるよう、取得元に依らずCSV本体を入力として扱います。一方で集約結果（`kpt-summary.md`）は、GitHub上で表として読めて人間のレビューに有利なためMarkdown表のままにしています。

### なぜspec.mdをシステム非依存のMarkdown形式にしたか

プロセス自体（Issueテンプレートやカスタムエージェント）はGitHub Copilot Coding Agentに強く依存しますが、成果物であるspec.mdは他のツール（Notion、Jira、他のSDDツールなど）にそのまま転記・移植できるよう、特定システムの記法に依存しない見出し構造のみのフォーマットにしています。プロセスの可搬性を高めるため、`docs/process/prototype-driven-flow.md`にGitHubに依存しない手順書も別途用意しています。

### なぜプロトタイプ→KPTのループがspec.md生成後も終わらない設計にしたか

spec.mdの生成を「開発の終点」として扱うと、生成後に得られた新しい気づき（KPT）を反映する仕組みがなくなってしまいます。そのため、spec.md生成はあくまで「その時点のスナップショット」と位置づけ、以降もプロトタイプの改善とKPTの記入は継続し、spec.mdとの差分は`change-history-logging`スキルを通じて追記していく運用にしています。

### なぜ仕様（spec.md）とデザインルール（rule.md）を分離したか

`spec.md`は他ツール（Notion / Jira 等）へ転記できるシステム非依存のWHATを狙っています。ここに配色・余白・遷移などのデザインルールを混ぜると、実装スタックへの依存が仕様に染み出し、可搬性という設計意図に反します。またデザインルールは複数の仕様から参照される共有資産になりうるため、仕様に複製するとドリフト（不整合）を招きます。そこで見た目・操作感のルールは`rule.md`（`design-rule-template`スキル）に分離し、`spec.md`は仕様のみを保持します。さらに、`spec.md`は人間の判断で確定・`rule.md`は承認なしで適宜更新という**確定の仕方も非対称**にしています。KPT項目には集約時に`対象`（`spec`/`rule`）を付与して、どちらの成果物を改善する材料かを追跡します。

### なぜデザインルールを最初から3層（spec/rule/design）にしなかったか

当初は「基本デザインルール（共有）＝`design.md`」と「機能独自デザインルール＝`rule.md`」を同時に立てる案も検討しました。しかし「基本＝横断的に共通」かどうかは複数featureが揃って初めて判断でき、feature が少ない初期は事実上すべて`rule.md`に溜まります。共有の`design.md`を先に作ると中身が育たないまま形骸化します。そこで段階導入とし、本フェーズは`spec.md`＋`rule.md`の2層で回します。`design.md`への昇格は、複数featureの`rule.md`が揃い共通化が実証された段階で人間が別途判断します（Phase 2）。

### なぜ「対象」をagentが付与し安定化させるのか

KPT項目を`spec`/`rule`に振り分ける「対象」を人間に書かせると記述負荷が増えます（IDを人間に振らせない方針と同じ）。そのため対象は`kpt-agent`が集約時に付与します。ただし対象判定はラウンドごとに揺れると成果物の振り分けが不安定になるため、一度確定した対象は同一IDで再利用し、迷ったら`spec`を既定とするデフォルト規則を置いて、真に判別不能なものだけを質問化して往復コストを抑えています。
